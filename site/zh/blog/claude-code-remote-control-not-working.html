Claude Code Remote Control 连不上/卡住不动？3 个原因和对应解法

图标从绿点变灰，或者手机端一直转圈没有任何输出。这多半不是 bug，而是本地进程被下面三件事之一杀掉了。先判断是哪种，再对症下药。

先给结论

如果昨天还好好的，今天突然卡住不动，最大概率的原因是：电脑断网持续了大约 10 分钟以上，Remote Control 会话判定超时，本地进程直接退出了。（来源，官方文档）这是文档里写明的设计行为，不是缺陷。解法很简单：回到电脑前重新执行一遍 claude remote-control。

Remote Control 目前是 research preview（预览特性），Pro/Max/Team/Enterprise 都能用，但 Team/Enterprise 账号默认是关的，要管理员手动打开。（来源，官方文档）如果超时不是你遇到的情况，下面表格里还有另外两个常见死因。

能杀死 Remote Control 会话的三件事

原因你会看到什么为什么会这样
断网超时 图标从绿变灰，之后一直没有任何新输出，怎么等都没用 断网持续约 10 分钟以上，会话判超时，本地 claude 进程直接退出（来源，官方文档）
进程被杀 症状一样，但发生在你关掉终端窗口、退出 VS Code，或电脑刚合盖睡眠之后 Remote Control 本身就是挂在那个终端/编辑器会话上的本地进程，进程一死，手机那头就没人可对话了（来源，官方文档）
电脑还在唤醒中 打开电脑的头 10~30 秒转圈，之后自己好了 电脑刚从睡眠唤醒，重连还在追赶进度

不需要额外东西的解法

  • 重新起一次。回到终端再执行一遍 claude remote-control——超时和进程被杀这两种情况都靠这一招。
  • 把它包进 tmux 或 screen 里跑。官方文档本身就建议在终端复用器里启动 Remote Control，这样关掉终端窗口不会连带杀死底层进程。（来源，官方文档）
  • 不让电脑睡眠。macOS 出门前跑一下 caffeinate，或者直接在电源设置里关掉自动睡眠。
  • 信号不稳时用手机热点兜底。家里/公司 WiFi 经常掉线的话，这治不了那个 10 分钟的超时线，但能减少你撞上它的次数。

这些解法解决不了的部分

tmux 保住的是"进程还活着"，不代表手机端会自动重新接上那个会话——回来后你可能还是要手动执行一遍 claude remote-control --continue。不让电脑睡眠这件事，坐在桌前很容易，出差在飞机上就很难顾上；而且大多数笔记本合上盖子会强制睡眠，跟电源设置怎么调都没关系。热点能缓解 WiFi 不稳，但只要你所在的地方彻底没信号超过十分钟，它就无能为力了。

如果你真正想要的是"电脑可以直接关机"，Remote Control 从设计上就不是干这个的——官方文档给的方案是改用 Cloud sessions，任务跑在 Anthropic 自己的基础设施上，而不是你的笔记本上。（来源，官方文档）上面几条解法都改变不了这一点：它们都还是假设你的电脑是开着的。

如果你要的是"不设超时、不用手动重启"

上面每一条解法管理的都是一个仍然可能死掉的进程——只是让它更不容易死，或者把"发现它死了"这件事甩给你自己去做。如果你要的是一个能扛住任意时长离线、回来自动接上而不用你动手的会话，那需要的是不同的架构，不是把超时线拉长。

PocketShell 是围着这个思路做的自托管方案：你机器上的 tmux 会话才是真身，手机跟它的连接只是一条可以断的线。离线期间输出照常写进服务端的环形缓冲，重连时按序号把你错过的部分补发回来，不依赖同一个浏览器标签页或同一次 App 会话一直开着——这不是一个可以调的超时策略，是记录"你不在的时候发生了什么"的另一种方式。

说清楚它解决不了什么：PocketShell 同样不是云端托管。跑它的那台机器一断电，任务照样停，这点和任何自托管方案一样，也和上面官方的 Cloud sessions 不同。它去掉的只是"手机这头网络不稳"这件事本身会杀死会话。
